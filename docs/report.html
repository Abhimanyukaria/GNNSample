What was built

The sampler takes a CSC graph and a batch of seed nodes and returns the 3-hop sampled subgraph in the layout PyG's NeighborLoader produces: each hop expands only the nodes discovered by the previous one, picks up to k in-neighbours without replacement (Floyd's algorithm), deduplicates the frontier and assigns local ids in order of first appearance.

Random draws come from a counter-based Philox generator keyed on (seed, hop, node, draw), so results do not depend on thread mapping or device. The CPU (SYCL) and iGPU builds return byte-identical subgraphs, and a NumPy reference sampler is the source of truth in tests. Features are gathered on the GPU from a zero-copy host table and written straight into PyTorch XPU tensors, so nothing crosses between CPU and GPU except seed ids and per-hop counts.

Stack: Intel DPC++ 2026.1.0 (matched to PyTorch 2.14.1+xpu's SYCL runtime), nanobind, PyG 2.8.1 / pyg-lib 0.9.0 as the baseline, all in Docker on WSL2.

Per-minibatch sampling vs pyg-lib

At scale: Twitter-2010

Twitter-2010 has 41.7 M nodes and 1.47 B edges; its CSC is 6.2 GB, the largest graph this laptop can hold. We decoded the publisher's transposed WebGraph file straight into an in-neighbour CSC (about 4 minutes, 1,468,364,884 edges: the published count minus 298 self loops) and sampled the same seed batches with both samplers. Seeds are a random 1% of nodes, the convention gSampler uses for graphs without a training split.

Final against v1 is 0.569 when paired batch by batch (1.76×), in line with the smaller graphs, so the optimizations hold at 1.47 B edges. Against pyg-lib the two samplers had to run in separate processes for memory reasons, so that ratio is not interleaved; both runs were on AC power and drew about 175 K edges per minibatch.

A memory trap specific to WSL2. The iGPU's device memory is allocated on the Windows side, outside the Linux VM's limit. The first attempt read the 5.9 GB edge file through the VM's page cache while copying it to the device; together with Windows that exceeded the laptop's 15.5 GB, Windows paged the VM out and Docker stopped responding. The loader now streams the file to the device in 64 MB chunks and drops each chunk from the page cache. Windows' free memory then bottomed at 337 MB during the load and settled at 1.3–2.3 GB, which is the practical ceiling of this machine.

Where the sampler's GPU time goes

Is sampling the bottleneck? Three measurements

Before writing kernels we measured where a PyG training step spends its time. The first two answers were wrong, for reasons worth knowing.

1. Sampling looked like 7% of the step. The model ran every layer over all ~410 K sampled nodes. With layer trimming (each layer computes only what later layers need) the GraphSAGE step fell from 1.91 s to 0.30 s on the iGPU.

2. Feature gather looked like 47%. That was our bug: pandas returned the feature table column-major, so every row gather touched 100 cache lines. Fixed, the gather takes 38 ms.

3. Corrected: sampling is 30% of a PyG step and data preparation 49%. Our pipeline cuts data preparation from about 232 ms to about 43 ms.

Training step against PyG at its best

Real PyG overlaps CPU sampling with GPU training through DataLoader workers, so the fair baseline is wall time per step with workers. Ours samples minibatch i+1 on its own queue while PyTorch trains minibatch i.

The step is 1.35× faster on the mean and 1.20× on the median. It cannot go much further on this laptop: model compute on the iGPU is about 235 ms of every step, so even free data preparation caps the gain near 1.6× (Amdahl). Overlap adds only ~4% here because our kernels and PyTorch's share the same 64 execution units and memory bandwidth.

Limitations and next steps

One laptop iGPU. All results come from a 15 W Intel iGPU under WSL2, where a host sync costs ~0.6 ms and training is slow. The gap to PyG should widen on a discrete GPU, where data preparation dominates the step (published: sampling is 46–96% of PyG/DGL steps on V100/A100), but that is a projection until measured.

No GPU state-of-the-art comparison yet. DGL GraphBolt, gSampler and cuGraph-PyG run only on CUDA. Our expected standing: competitive with DGL's GPU sampler on kernels, likely behind gSampler, behind GraphBolt end to end until overlap is measured on a discrete GPU. Phase 4b ports the SYCL code to the CUDA backend and runs all of them, plus a plain-CUDA control kernel to price SYCL.

Scale. Twitter-2010 is the largest graph this laptop holds, and only for sampling: end-to-end training would also need features for 41.7 M nodes, which do not fit beside the graph. Friendster's CSC alone is ~15 GB and needs a larger machine.

Measurement hygiene. Two runs were affected by host conditions (battery throttling, CPU contention); their absolute numbers are excluded. Every log now records the power state, every long run has a timeout, and a watcher checks progress every 5 minutes.
